# CUJAMMU-PULSE: Deep Risk and Resolution Review

Review date: 2 October 2026 | Baseline: architecture v1.4 | Status: static review and proposed resolution plan.

## 1. Conclusion and evidence boundary

The platform has a viable target architecture, but the prototype is not ready for real university personal data or production use. The highest priorities are verified role provisioning, resource-scoped API authorization, private response/file handling, one attendance truth, transactional capacity/calendar rules and authoritative feature controls. Thirty-day deletion needs provider-backed evidence, not a scheduler alone. Shared app/web screens are still a migration target rather than current source behavior.

This review contains **60 prioritized findings**. It is a catalogue of identified issues and plausible failure modes, not a claim that every undiscovered vulnerability has been found. Code observations were rechecked through read-only source inspection; three independent reviewers covered identity/attendance, runtime/media and data/operations. No database records, uploads or user secrets were inspected. No fresh build, running application, exploit, penetration test, load test or native-device test was executed. A risky source pattern is not the same as a captured successful exploit.

Classification: **C** = confirmed source/configuration observation; **G** = unresolved design detail or documentation conflict; **R** = operational/residual risk that cannot be eliminated by a design promise. **P0** = blocks a real-data pilot; **P1** = must be resolved/proven before the affected production module; **P2** = planned reliability/usability improvement. Proposed solutions below are not implemented fixes.

Current scope is 29 active requirements CF-01..30 excluding retired CF-12. No retired module is restored by this report. Current normative documents are [main architecture](UNIVERSITY_PLATFORM_ARCHITECTURE.md), [core requirements](CORE_FEATURES_SPEC.md), [event operations](EVENT_OPERATIONS_AND_ATTENDANCE_SPEC.md), [lifecycle/notifications](SCHEDULING_AND_NOTIFICATION_SPEC.md), [runtime/media](RUNTIME_FEATURES_AND_MEDIA_SPEC.md), [acceptance contract](PLATFORM_PARITY_AND_ACCEPTANCE.md) and [agent rules](AGENTS.md).

## 9. Recommended implementation order and ownership

Additional source evidence for R03/R16: `QRService.java:35-52` embeds plaintext identity/token; `AttendanceService.java:46` logs the token; `AttendanceController.java:23-37` renders a registration and regenerates QR through a publicly permitted operational verification path. Separate public certificate verification from private admission credentials, remove secret logging and audit/rotate exposed active credentials during authorized remediation. The current exposure pattern is statically confirmed; actual unauthorized rendered response must still be tested in isolated synthetic staging.

Priority documentation clarifications are: Files/backups table versus transient storage, scan service versus human end-to-end SLO, hold/purge serialization cutoff, generated-document lifetime/authenticity and registry example scenario mismatch. This review reports those amendments; the canonical architecture is not silently rewritten and no new user feature is added.

1. **Before real data:** resolve R01-R06, R09/R11, R13 and AI private-context isolation; reproducible build baseline. Owners: security lead, identity/backend engineers, shared-client engineer and independent reviewer. No production imports or deployment are implied by this review.
2. **Correctness foundation:** one complete registration + booking + attendance path, scoped guards/indices and audit/outbox; explicitly test all three attendance modes and manual/QR separation. Owners: backend/DBA/QA plus event office. Do not implement several parallel attendance truths.
3. **Runtime/retention proof:** one end-to-end administrator toggle across two servers and two clients; one private upload through expiry/purge/restore. Fix the Files table conflict, formalize hold cutoff/generated-artifact matrix and provider capability before spreading storage patterns.
4. **Campus operation proof:** postpone/cancel/resource suggestions, notification fan-out, gate throughput and safe-off/drains under disruptions; pilot synthetic then authorized minimal real data. Owners: SRE, gate operator/campus hardware and assigned office.
5. **Module rollout and security gate:** extend the proven contracts to hostel/chat/sports/academic/alumni/support; shared phone-compatible workflows, office UAT and independent authenticated assessment/retest. Do not call unfinished functions complete to meet a date.

Root/global guard granularity, evidence sufficiency and media/provider retention need written ADRs before relevant implementation, because changing these later affects correctness. Most risks already have a direction in v1.4; the missing part is concrete configuration, code and evidence.

## 10. Capacity reasoning and practical suggestions

Gate capacity includes humans. Illustrative calculation only: 2,000 arrivals in 10 minutes mean 3.33 arrivals/second. If complete decode+proof+identity+movement takes 8 seconds at one gate, theoretical capacity is 0.125 person/second/gate: at least 27 gates at full utilization, about 39 at 70% utilization. These are assumed example inputs, not measured campus numbers. Improve arrival staggering, prereadiness, scanner placement and supervised fallback before relaxing security. Measure actual service distribution, not only average API latency.

Storage estimate uses accepted bytes/day × 30 plus derivative multiplier, processing scratch, justified holds and purge/recovery overhead. Uploads of 50 GB/day alone mean about 1.5 TB of originals at steady state before additions; illustrative only. Size quotas, compression profiles and worker/delete throughput are capacity controls; a 30-day rule does not mean negligible storage.

Add operational features through existing modules rather than widening scope: clear `Why disabled?`/`Why under review?`, operator permission expiry/countdown, notification delivery summary, evidence-quality badges, report revision metadata, media-expiry warning and tested non-AI support fallback. Use deterministic suggestions and checklist warnings before ML predictions. No facial-recognition/continuous location or automatic discipline.
