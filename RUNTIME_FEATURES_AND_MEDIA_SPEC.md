# CUJAMMU-PULSE: Runtime Administration and 30-Day Media Lifecycle

Version 1.4 | 2 October 2026 | Normative implementation design; not deployed behavior.

Read with [UNIVERSITY_PLATFORM_ARCHITECTURE.md](UNIVERSITY_PLATFORM_ARCHITECTURE.md), [CORE_FEATURES_SPEC.md](CORE_FEATURES_SPEC.md), [EVENT_OPERATIONS_AND_ATTENDANCE_SPEC.md](EVENT_OPERATIONS_AND_ATTENDANCE_SPEC.md), [SCHEDULING_AND_NOTIFICATION_SPEC.md](SCHEDULING_AND_NOTIFICATION_SPEC.md), [PLATFORM_PARITY_AND_ACCEPTANCE.md](PLATFORM_PARITY_AND_ACCEPTANCE.md) and [AGENTS.md](AGENTS.md). CF-29 adds runtime administration; CF-30 adds uploaded-media expiry. CF-12 is retired and must not be reused. There are 29 active requirement IDs in CF-01..30 excluding CF-12.

## 1. Scope and no-update contract

Authorized university administrators control **every registered business module, feature and user-facing function** from `Admin -> Module & Feature Controls` on both web and Android. Every catalog row has an Enable/Disable switch, current effective state, scope, dependencies, last change and propagation status. Changes are runtime configuration, not source edits, a new APK, a web build or an app-store update.

This applies to functionality already implemented and installed in **both compatible clients** with available backend handlers and migrations. Enabling cannot create missing software, native permissions/dependencies or an unsupported function in an older app. Missing/incompatible implementations are visibly `Unavailable in this release`; do not display a working ON switch or fabricate success. A newly built feature needs its first compatible release before it can be toggled thereafter. Serve needed shared assets on demand and avoid stale navigation caches; no forced install/restart is required for supported ordinary runtime changes.

An authorized administrator on a compatible **control-plane** client can always request OFF for an existing catalog key even when that business feature is unsupported in their own client renderer. Target-feature compatibility gates ON/execution, not emergency disable/recovery. The catalog uses stable generic controls, so an unavailable feature screen cannot block the OFF switch.

An admin disable hides the feature's navigation, cards, buttons, walkthrough steps, search results, notification action links, assistant tools and applicable routes for ordinary users on both clients; backend APIs, subscriptions, jobs and exports also enforce OFF. Re-enable restores the appropriate screens/actions using retained permitted records, **subject to user RBAC and resource scope**. A feature flag never grants an organizer, student or admin rights they do not hold. Enabling attendance at university level does not enable a volunteer scanner master or grant manual authority.

Removing a module from the product catalog is different from temporarily setting OFF: removed modules have no toggle, routing, API, AI tool, event template or planned collection in the target product. Feature-disable never deletes domain history. Thirty-day media expiry remains active regardless of module visibility.

## 2. Authoritative feature registry

Each module/feature/function has a stable featureKey, type MODULE/FEATURE/ACTION, parent key, explicit required dependencies, supported client/backend version range, default, risk classification, permitted config scopes, immutable safety classification and safe-disable handler. Shared screen/action/API registry references the same keys; CI rejects any exposed business action or backend handler lacking coverage. Config scopes are institution-wide by default, with campus/department/event overrides only when authorized; a child/override cannot turn ON beneath an OFF ancestor or hard dependency.

Effective permission is:

`implemented compatible capability AND enabled module AND enabled feature/action AND enabled required dependencies AND user capability/resource scope AND valid domain state/window/control`.

For example `events -> attendance -> qr.scan` and `events -> volunteers -> recruit` have distinct function controls. `attendance.manual` and `attendance.export` are separate controls. `academic.scorecards.download`, `chat.attach`, `polls.vote`, `library.export`, `hostel.apply` and `assistant.actions` are independently catalogued. Pure implementation internals are not fake user functions; changing encryption, identity validation or database invariants is not a product toggle.

Unknown key, malformed/unsigned configuration, missing authoritative version or unsupported dependency fails closed for the affected business function. Client receives only its authorized evaluated manifest, not internal targeting conditions or other departments' settings. Backend evaluates trusted config, never client-provided `enabled=true`, role selections, rollout audience or cached screen state.

Core identity/access checks, audit custody, administrator recovery/control-plane access, mandatory media purge, safe physical exit and incident containment are protected foundations, visibly marked `Required safety control`. Their presentation has a locked indicator/explanation rather than a deceptive switch that disables security. All actual business functions retain toggles. This prevents an admin accidentally locking every administrator out, stopping mandatory cleanup or allowing unauthenticated access while still offering whole-platform maintenance for ordinary users. Recovery console is restricted separately and audited; AI cannot operate feature-control authority.

## 3. Admin panel and toggle workflow

Search/filter by module, enabled/disabled, dependency, campus and compatible release. Module hierarchy expands into every feature/function row with accessible labelled switch, ON/OFF state, actual effective state and explanatory blocked reason. Small screens use the same hierarchy/actions and review sheet; keyboard/screen-reader operation and text status are mandatory.

`Toggle -> impact preview -> confirm when needed -> server commit -> live propagation -> effective status`. Low-impact independent presentation functions can commit directly; disruptive module changes show affected users, active visits/passes/attendance windows, dependent functions and a concise reason field before the same final toggle action. No code editor or arbitrary scripts. Restrict bulk disable/enable to a reviewed scope and atomic config revision; child selection cannot accidentally affect another institution.

Requested ON/OFF is distinct from effective ENABLED/DISABLED/DRAINING/DEPENDENCY_BLOCKED/INCOMPATIBLE/ERROR. Optimistic spinner is not committed success. Concurrent administrators use expected config revision/If-Match and idempotency; conflicts show current state rather than last-writer silently overriding changes. Audit actor, scope, keys, old/new values, safe reason, dependency impact and revision. Only verified feature.manage authority within institution/scope can mutate; privileged sessions/MFA follow the existing identity policy. Control changes notify relevant office owners/operators, not every student for cosmetic changes.

## 4. Live propagation and server enforcement

MongoDB `featureDefinitions`, `featureConfigurations`, `featureConfigRevisions` and `featureChangeJobs` hold canonical data. Effective revision, audit and outbox commit in one transaction. Realtime gateway publishes a safe invalidation with monotonic revision to authorized clients/services; they fetch current evaluated manifest. Browser uses BFF session; native uses its secure authenticated transport. Local/Redis cache is a projection, never authority for an irreversible mutation.

Connected-client propagation design target: p99 <=5 seconds after committed config under measured approved load. Reconnect/foreground fetches current manifest; bounded polling fallback (initially <=30 seconds while online) handles a missed live event. Out-of-order events cannot reinstall older configuration. An offline/disconnected app cannot receive instantaneous changes: label configuration stale and do not start sensitive disabled-unknown actions; server enforces latest OFF on reconnect even when old UI temporarily remains. Disable removes in-memory routes/queries, stops relevant realtime subscriptions and evicts private cached views. Re-enable refetches authoritative permitted state, not discarded stale success.

Each mutation linearizes against all applicable config/control revisions: short transaction guard writes or a separately proven equivalent coordinator serialize accepted business mutations versus OFF. A cache check before transaction cannot prevent a race. Scope guards and stable ordering address dependencies; load-test contention rather than assuming free global locks. A mutation committed before OFF is valid history; queued subsequent user operations must recheck current configuration. Ongoing reads/streams and downloads recheck feature/access/expiry before delivery and at safe chunk boundaries; already delivered data cannot be recalled.

Background jobs, webhook/provider adapters, exports, scheduled reminders and assistant tools use the same keys/current policy. A disabled function may not keep running because only its button was hidden. Durable mandatory safety, cleanup, audit and recovery jobs use explicitly protected system purposes, not ordinary business bypasses. Notification inbox may deliver an actionable service-disabled/update notice, but disabled feature deep links do not reopen the function. Denials use safe `FEATURE_DISABLED`, `DEPENDENCY_DISABLED`, `CONFIG_STALE` or `CLIENT_INCOMPATIBLE` status and available support route.

An OpenFeature-compatible evaluation adapter is a candidate integration, not a new required hosted service or replacement for scoped backend authority: [OpenFeature evaluation API](https://openfeature.dev/specification/sections/flag-evaluation/). No personal targeting data is exported to a third party by default.

## 5. Dependencies and safe disable

Hard dependencies block dependent new actions; optional integrations degrade gracefully. The preview enumerates effects and the effective manifest explains them. Example: switching OFF event registration stops new admissions, while permitted organizer lifecycle management still handles already committed participants. OFF for QR scanning preserves independent authorized manual fallback only when manual remains ON and policy permits it; it never silently turns manual ON. Disabling media upload does not stop file expiry. Disabling assistant actions can leave safe public FAQ answers if those independent functions remain enabled.

For active operations, OFF first prevents new work, invalidates credentials/delegated scopes where needed and creates a bounded drain/reconciliation job. Ordinary module navigation disappears promptly, while protected minimal continuity actions (close an existing library visit, record safe exit, contact helpdesk) remain available in an explicit `Active Session / Service Notice` recovery surface. They cannot create new visits, attendance or approvals. No physical egress depends on feature visibility. Show affected owners DRAINING with deadline/responsible operator; a failed drain escalates rather than losing records.

If a function cannot be disabled safely in the current state, immediately fence new actions and return an honest bounded transition rather than claiming complete OFF. Enable waits for compatible backend/data policy and necessary reconciliation. It does not restore removed permissions, reopen prior event attendance windows or resurrect expired/deleted media. Institution admin controls remain distinct from faculty event scanner controls; both must authorize an applicable action.

## 6. Thirty-day uploaded-media rule

All user/institution-uploaded media bytes expire at `uploadAcceptedAt + 30 * 24 hours`, using server UTC, not thirty local midnights. Includes profile photos, event banners/gallery, chat/feed attachments, lost/found images, ticket evidence, audio/video and **uploaded PDFs/documents such as scorecard batches**. Original accepted upload timestamp is immutable; view/download/share/module re-enable/edit/re-encode, moving references or generating a thumbnail does not reset the deadline. Replacement is a genuinely new upload with its own deadline; repeated identical-upload abuse is limited by quota, idempotency and same-upload lineage, not an unlimited expiry-reset operation.

Derivatives inherit the original deadline: thumbnails, previews, OCR/extracted searchable content retaining file data, resized/transcoded media, separated PDF pages, temporary processor outputs, exports containing those uploaded bytes and cached versions. A download already on a user's personal device or a recipient's own copy is outside platform custody; do not claim remote deletion of those files. Stable immutable application branding shipped as code assets is not a user upload and needs its release lifecycle; administrator-uploaded replacements obey the rule.

UI shows `Available until <date/time>` before upload and on attachment/PDF preview. After expiry use a placeholder `Media expired after 30 days`; do not show broken links or silently regenerate it from a stale copy. Profile returns to default avatar. A chat/post/ticket retains only permitted text/minimal metadata under its separate policy; attendance and verified structured SGPA/CGPA records are not uploaded media bytes and retain institution-approved structured-record policy. Never copy file content into MongoDB, logs, prompt archives or vector indexes to bypass deletion.

Academic PDF copies and original batches are not permanent archives in this platform. Preserve approved structured result versions/provenance; if the institution requires permanent official originals, use a separately governed university official archive outside this 30-day transient storage and retain a scoped retrieval reference. No automatic export of real records is authorized here. The student must see whether a PDF will expire and whether an external official archive is available; missing integration means PDF download becomes unavailable after expiry, not a false promise of lifelong download.

An authorized, evidenced legal/incident preservation hold is the sole protected retention exception when applicable obligations require it. Record owner, scope, reason, access, review deadline and release audit; hold data goes to restricted exception custody excluded from ordinary access. A normal admin toggle, enabled feature or ordinary user cannot extend retention. Required applicability/office policy must be validated before production; no generic unlimited hold or silent exception for every file. Release an expired hold into immediate purge. The 30-day rule covers normal uploaded storage; held evidence is truthfully reported as HELD, not PURGED.

## 7. Expiry, permanent purge and storage efficiency

At exact expiry, independent server access checks deny preview/download/AI retrieval even if the purge worker is delayed. Do not depend on Mongo TTL or object-store lifecycle timing. Use a private delivery gateway or short-lived capped access mechanism with expiry never beyond remaining media lifetime; provider-signed URLs that cannot revalidate revocation are not a substitute for strict boundary policy. CDN/private caches have no public immutable media URLs, bounded lifetime and expiry/purge controls. Module OFF and object deletion also invalidate live access grants. The current local cleanup worker deletes only metadata-tracked expired objects; it does not infer expiry from filesystem timestamps or sweep untracked paths, because orphan cleanup requires a separate inventory workflow that cannot risk deleting held or unrelated data.

States: UPLOADING/QUARANTINED -> READY -> EXPIRED -> PURGING -> PURGED, with HELD and PURGE_FAILED branches. Independent durable sweeper scans indexed expiresAt/state, claims leases and emits idempotent per-media deletion jobs. Catch up missed periods, retry with bounded backoff and alert on missed targets. The local implementation keeps failed metadata rows in `PURGE_FAILED` with bounded error text and retries them on later sweeps; it never reports `PURGED` solely because a deletion attempt was queued. Deletion blocks a concurrently finishing upload/transcode/preview job from republishing expired data: finalize checks lineage expiry/state/version and deletes late outputs. Quarantine and abandoned multipart uploads have shorter operational cleanup, bounded by the same ultimate deadline.

Purge all original objects and object versions/delete markers, derivatives, multipart remnants, regional replicas, processor scratch space, caches, search/vector fragments and platform-held offline copies when connected. Do not call creating a delete marker permanent deletion. Record per-store proof/provider confirmation and a bounded minimal tombstone, not retained file content. A nonversioned transient bucket is preferable where appropriate; replicas/backups still need explicit treatment. Object-lock/hold settings must match the deliberate restricted exception model.

For provider behavior, [S3 expiration considerations](https://docs.aws.amazon.com/us_en/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html) describe asynchronous expiration and version handling; [deleting object versions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html) explains why ordinary delete can retain old versions. Equivalent guarantees must be verified for the selected storage provider. Bucket lifecycle is a defense and cost cleanup, not precise access-expiry authority.

Normal uploaded media is excluded from general long-lived database/system backups. Any media replication/recovery copy inherits its original deadline; a backup made on day 29 cannot retain its file for another 30 days. Restore consults a separately protected monotonic expiry/deletion ledger before serving bytes and replays pending deletion, never resurrecting media or its decryption material. If a provider cannot physically purge backup copies on the required schedule, use a separately reviewed per-object cryptographic-erasure design that irreversibly removes every recoverable key copy at expiry, and disclose remaining ciphertext purge; do not claim normal KMS rotation or recoverable escrow achieves this. Provider qualification and tested deletion evidence are release blockers for the claimed retention behavior.

Design targets: deny normal access at expiry; begin purge promptly and complete normal online managed-copy deletion within 24 hours after expiry at p99 under approved load. Display EXPIRED/PURGING/FAILED until verified completion; PURGED means all required platform stores completed deletion or approved irreversible-erasure criteria, never merely queued. An asynchronous infrastructure cannot promise exact-instant physical byte destruction at day 30. Monitor maximum overdue age/bytes and held exception volume; tighten provider/worker targets if university requires stricter deletion. Recovery from a failed purge is operational action, not restoring expired access.

Efficiency: pre-upload allowed MIME/size/count quotas, bounded malware/parser checks, image/video dimension/duration limits, reviewed compression/transcode profiles and few necessary derivatives. Estimate output sizes, stop conversion bombs, stream uploads/downloads and do not store binaries in MongoDB. Private tenant-scoped dedupe is optional only if it preserves each reference's access and expiry and never leaks cross-user content existence; deletion scheduling cannot keep expired private copies through hidden references. Prefer disabling dedupe over ambiguous retention. Orphan sweeps and incomplete-upload cleanup prevent abandoned storage; storage dashboard shows active/expiring/held/overdue bytes and failure ownership.

## 8. Data, API, monitoring and verification

Add feature definitions/configurations/revisions, evaluated manifest versions and drain jobs. Media metadata records institution/owner/purpose/lineage, uploadAcceptedAt, immutable expiresAt, checksum, bytes, private object/version refs, hold, purge lease/state and verified-store completion. Compound indexes support tenant/feature scope, latest revisions and media expiry workers. Never rely on TTL deletion of metadata to clean up file bytes; keep minimal expiry/deletion evidence until backup-replay and audit rules are satisfied.

Commands: `/admin/features/catalog`, `/admin/features/config`, `/admin/features/changes`, `/me/features`, scoped `/media/uploads`, `/media/{id}/status`, protected `/admin/media/storage`, hold/release through separately justified authority and purge retry. Feature mutation expected revision/idempotency and media finalization immutable expiry/state checks are required. Staff dashboards expose useful counts/status, not public object paths or student files. Config authority is distinct from viewing private media.

Observe commit-to-client lag, stale manifest count, denied disabled actions, dependency conflicts, stuck drains, purge queue/latency/overdue bytes, object version inventory, cache fragments, multipart orphans, holds and restore resurrection attempts. Required jobs cannot be disabled by ordinary feature switches. Synthetic tests cover two administrators, missed/out-of-order updates, disconnected/old clients, backend/API/job/AI bypass attempts, module parent dependencies, ongoing visits and revoked volunteer scans. Media tests cover exact UTC boundary, derivatives/in-flight processors, URLs/caches/versions/replicas/backups, hold release and no-reset behavior. No live data deletion is authorized by this architecture-only update.
