# Durable mail intent in the JPA bridge

18 October 2026. CF-19 notification foundation; supersedes the volatile transport portion of `ADR_TRANSACTIONAL_MAIL_SNAPSHOTS.md`.

## Problem and scope

The former immutable HTML snapshot avoided concurrent Hibernate access but was still lost on a process crash between domain commit and asynchronous dispatch. Failed SMTP messages entered another in-memory queue, which also disappeared on restart and logged recipient/content details.

`EmailService` now persists a `mail_deliveries` record through a REQUIRED transaction before the owning domain commit. A failed persistence operation propagates; it cannot silently report a successful notification intent. Existing registration/event command transactions supply atomicity. Transactionless callers receive their own short persistence transaction. Event announcements up to 500 recipients use the inline path. Larger audiences create a durable recipient-ID snapshot in the same repeatable-read approval transaction, capped at 20,000, and a scheduler drains it in 100-recipient transactions. Approval fails closed above that bound or if the snapshot count changes during approval.

## Invariants

- Payload is a recipient account ID/address snapshot, an allowlisted notification kind, and only the source IDs needed for freshness checks (event ID, scheduled-time snapshot and event lifecycle version for event notices; registration ID for registration/waitlist/promotion/withdrawal/attendance notices). No arbitrary subject, HTML, user message, event title, marksheet content, OTP or reset secret enters this table. The fixed message links to the authenticated dashboard where current authorization applies. Legacy bulk announcement emails therefore signal an account update; their body is not an archival or guaranteed private-inbox channel.
- Before an event lifecycle notice is leased, the worker locks and reads its source event, then suppresses it if the event is missing, unscoped, no longer in the status implied by the notice, has a different schedule where applicable, or has a different monotonic lifecycle version. Event mutations in `EventService` use the same row lock and flush the version before queuing a notice. The version check prevents an A-to-B-to-A schedule change from reviving an older notice on this JPA path. Registration-linked notices are checked against the current registration status and account owner; positive registration/waitlist/promotion notices also require the event to remain approved. Withdrawal and attendance notices remain eligible after event cancellation when the registration is still in the relevant terminal state. Legacy event-kind and registration-kind rows without source context fail closed. Registration claim checks are still not serialized with all registration writers; Mongo concurrency and deployed migration evidence remain open release gates.
- `ATTENDANCE_UPDATE` requires the domain command to persist `ATTENDED` before enqueueing in the same transaction; a pre-transition call is suppressed at claim. No current attendance workflow calls this producer, so this remains a contract tested in isolation rather than an end-to-end attendance notification claim.
- A committed intent survives process restarts. An uncommitted/rolled-back intent cannot be claimed. No entity/proxy crosses the dispatch boundary.
- Large announcement campaigns snapshot only recipient account IDs, event ID/date/version and optional verified department ID. A row lock serializes workers for one campaign; each batch commits the outbox rows and increments campaign progress while deleting the processed recipient IDs in the same transaction. A crash before commit therefore replays that batch; a committed batch cannot be enqueued a second time. The worker rechecks account enablement, student role and verified-department binding before creating the private mail snapshot, and the mail claim repeats the role/department check under a user-row lock. A changed event suppresses the remainder. Disabled event/notification controls pause dispatch, while unfinished audience IDs are suppressed and erased in bounded batches after seven days. Terminal campaign metadata is removed after 30 days. This SQL/JPA behavior still needs equivalent Mongo replica-set transactions and concurrency proof.
- A worker takes at most 25 due records per cycle. A short locked transaction checks account enabled/address unchanged, then authoritative controls/source rows in domain lock order (`MODULE_EVENTS`, `MODULE_CERTIFICATES` for certificate notices, source event/registration row where applicable, then `MODULE_NOTIFICATIONS`) before claiming a 120-second lease with a new random token. Event lifecycle writers lock the event row before writing inbox notices; the worker uses the same order to avoid a feature-row/event-row cycle. Certificate finalization locks event and certificate controls before inbox notifications; certificate claims follow that sequence to avoid control-row/source-row inversions. A completion from an old lease cannot overwrite a newer claim. Abandoned leases are retried, with at most five attempts and bounded exponential delay. Database failures leave a durable row for reconciliation rather than discarding it.
- SMTP runs outside domain/claim/completion transactions. Default existing SMTP connection/read/write timeouts are five seconds each. Operational overrides must remain shorter than the lease; DNS/provider behavior still requires deployment qualification. A hung process must not be treated as a verified delivery.
- A stable delivery UUID is used as the SMTP Message-ID. It is not an exactly-once guarantee: provider acceptance followed by process/DB failure may cause a duplicate on retry. Domain request idempotency remains the command's responsibility; this slice does not invent deduplication by hashing private HTML or suppress distinct legitimate commands.
- QUEUED, LEASED, RETRY, PROVIDER_ACCEPTED, SUPPRESSED, DEAD_LETTER and EXPIRED are distinct. SMTP success means provider acceptance only. There are no fabricated delivered/read receipts. Console, professor-demo, missing sender and unsafe public-link configuration suppress external sending truthfully.
- Dispatch authorization linearizes at claim. An SMTP request already authorized/in flight cannot be recalled after a later flag/account change; the payload intentionally has no private resource details. Generic notices never restore resource access. The provider receipt/webhook and full function-level revocation architecture remain open work.
- Recipient addresses are cleared immediately at terminal outcome. The 24-hour operational lifetime blocks further dispatch; independent bounded cleanup removes expired payloads even with business notifications disabled. Cleanup is asynchronous and must be monitored under production load. Minimal structured delivery receipts become eligible for bounded deletion after 30 days; these are operational records, not the separately governed audit archive. Backup suppression, infrastructure custody and institutional retention qualification remain release work.
- Credential email uses a separate immediate single-attempt path. It never enters this generic durable outbox or retries after credential expiry. Password-reset email carries the bearer token only in one HTTPS reset link; it does not duplicate the token as visible body text. Reset-link creation and send-time dispatch require an exact host in `APP_RESET_LINK_HOSTS`; a blank list, HTTP origin, userinfo, query/fragment, nonstandard port or unapproved host suppresses reset delivery before token issuance. The generic forgot-password response remains unchanged. Provider exception messages/content and account addresses are not logged by this path. This does not make credential mail durable; a reviewed encrypted delivery design with institutional key custody is still required before retries can safely retain bearer material.

## Migration and recovery

This is an additive table/column set in the current SQL/JPA bridge, not completion of the target Mongo replica-set architecture. Local isolated H2 tests use schema generation. Production needs a reviewed additive schema migration for mail deliveries (including required recipient-role and verified-department scope), campaign roots and audience rows (including due/lease, expiry, runnable-campaign, terminal-cleanup and campaign-recipient indexes), deployment backup/rollback evidence and approved database encryption/access controls. Do not run destructive schema recreation against existing records.

There is no reliable import for a volatile queue already lost on restart. Stop the old dispatcher during a reviewed deployment and reconcile affected domain records rather than pretending their mail was delivered. Rollback to the old binary must not drop this table; the old worker will not drain it. Re-upgrade or a reviewed repair worker must reconcile pending rows.

The new transport does not close all CF-19 work: full notification trigger/audience inventory, scheduled reminder staleness suppression, recipient preference/priority/channel policies, signed provider callbacks, acknowledgement UI, operator dead-letter dashboard/alerts, real-user verified-department provisioning, campaign throughput/worker-race tests and production SMTP/security/load/DR evidence remain. The nullable source columns and event version require a reviewed additive production schema migration; no destructive schema recreation or `ddl-auto=update` acceptance is implied. No external SMTP was used during development.

## Verification

`EmailSnapshotTransactionTest` uses real H2 repositories and Spring transaction proxies with a mock SMTP sender: domain rollback, commit/immutable recipient, reconstruction after restart, transactionless durable enqueue, failed enqueue propagation, prohibition on transactional SMTP, concurrent claims, abandoned-lease fencing, bounded failure/dead-letter, demo suppression, account/address revocation, feature OFF, event status/date staleness suppression, expiry scrubbing and receipt cleanup. `EventServiceLifecycleNotificationTest` additionally snapshots 501 synthetic recipients, resumes five bounded batches, checks campaign completion, and verifies each recipient creates one outbox row while campaign audience IDs are removed. `CredentialEmailTest` verifies secret-bearing email never enters the retry service and provider failure text does not leak. Run results must be recorded after execution; source presence alone is not passing evidence.
